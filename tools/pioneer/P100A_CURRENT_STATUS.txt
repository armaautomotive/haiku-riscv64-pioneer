P100A / Qwen 27B: current status
================================
Updated November 7, 2026. Model: Qwen3.8-27B Q4_K_M.

The target is fast self-hosted inference, ideally 20 tokens/sec. It has NOT
been delivered, and 20 tokens/sec is unproven. A short 27B request runs all
model inference on the P100A, including attention and state; the CPU handles
files, preparation, vocabulary/text and lifecycle, not inference or fallback.

Latest real result
------------------
* Generation: 0.17290 tokens/sec, about 5.8 seconds per committed position.
* The unchanged fast run was 0.17281; these single runs do NOT prove a speedup.
* The answer counted from 1 through 14 before the 32-token output cap. This
  is one short response, not broad correctness or production qualification.
* Answer-ready took 35.11 minutes after Generate; this excludes prior source
  authentication. Weights were released at END. Warm Assistant is unfinished.

Measured generation bottlenecks
-------------------------------
The valid on-card profile attributes 48.85% of generation-body cycles to the
four projection-call phases, 33.67% to remaining recurrent+dense paths, and
11.87% to the output-head matrix. These are controller cycle shares, not
pure FPU/bandwidth measurements. Removing all projection time for free would
still yield only about 1.95x in that scoped breakdown, if everything else
stayed unchanged. No supported 116x route is established.

Four compact goals
-------------------
1. Identify the fastest engine's bottleneck: COMPLETE for one request.
2. Remove one measured overhead: TESTED/REJECTED as a meaningful gain.
   Descriptor reuse ran the complete 27B request but measured essentially
   the same speed. A native BFP4 matrix prototype passed a full-width K5120
   synthetic test on the P100A, measuring 24779/24803 card cycles for a
   preloaded 32-row band. This does NOT include GDDR loading and has NOT
   been integrated into the model or shown to improve model speed.
   Three real-weight bands pass the offline GDDR/compute observer. Their
   synthetic-input output errors are 8.6%–15.8%, so model quality remains
   an important open question before using the approximate format.
   The real-weight BFP4 diagnostic now runs on the card with GDDR loading:
   three K5120 bands returned all 192 expected BFP4 words, with each 32-row
   job taking 227142-227285 card cycles. This is NOT an equivalent-Q4 or
   full-model speed result: the conversion is lossy, and the BFP4 path is
   not integrated. See the physical report for scope and quality limits.
   A CPU comparison using the first prompt token's reconstructed layer-0 FFN input
   measured 5.7%-7.2% relative output error across those three bands versus
   the independent Q4 reference. This is not a full-model quality score.
   A CPU-only comparison of the complete first FFN block now shows 1.81%
   relative L2 error in the layer output for one prompt token. This is not
   a full-model quality result, a card measurement or a speed improvement.
   A separate FFN converter matches all 192 real tensor layouts without
   increasing their byte footprint and matches three card-tested bands.
   A real 7.2 MB fragment also passed a cold disk-cache conversion and a
   warm cache hit with zero source-row reads. This is not yet used by Work.
   A distinct 32-row BFP4 worker leaf now compiles and passes simulated
   RISC-V tests with inputs from ROOT L1 and converted weights from GDDR.
   It is NOT installed or integrated into full-model inference.
   A CPU-only full-token accuracy diagnostic completed all 64 layers with
   BFP4 FFN substitutions. Final logits differed by 35.9% relative L2,
   though both paths picked the same next token. This one-token result is a
   warning, not an answer-quality pass, and not a card speed measurement.
   Selective conversion of the first48 or last16 layers gave 24.8% and
   26.7% raw-logit differences, respectively, for the same token. The
   different layer counts and a single token prevent a general conclusion.
   The original-vs-all-BFP4 next-token distributions shared 3 of their top
   5 choices (KL 0.34466 nats, original-to-candidate) for that same token;
   this confirms more than a uniform logit shift, not general answer quality.
   A BFP4/BFP8 hybrid is under CPU study. With current 8192-token state and
   workspace, the existing seven-bank capacity arithmetic cannot fit BFP8
   for the last14 or more FFN layers while retaining all other allocations;
   last13 has a nonoverlapping offline repack proposal but lacks a real
   device allocator and loader.
   A new preparation-only page reader can use the existing BFP8 disk-cache
   format; nine pages from three bands of one real tensor matched fresh
   conversion. Full-model cache/upload remains unfinished.
   On one token, a last16-BFP8 numerical control improved top5 overlap to
   4/5 (KL 0.18387 nats), but exceeds that capacity bound. Last13-BFP8 gave
   3/5 and KL 0.37343, no improvement over all-BFP4 on this token. BFP8 in
   layers48..60 instead gave 4/5 and KL 0.20372, and has a fitting offline
   layout proposal. This is one token, not a quality or P100A speed pass.
   A BFP8 worker image and relocated BFP4/BFP8 job mapping now pass offline
   RV32/synthetic/three-real-sample tests. They are not connected to the
   live dispatcher or proven on the card.
   UPDATE Nov 7: a distinct experimental worker dispatcher is linked to both
   BFP4/BFP8 leaves and passes synthetic RV32/NoC/FPU simulation for both
   model widths. The BFP8 dispatch test uses a special layer-0 mask, not the
   proposed model mask. A simulation exposed staging overlapping the old
   GDN code location; the experimental image moves that code to 0x170000.
   Full peer-memory ownership, input lifetime, ROOT coordination, cache
   loading, on-card execution, model quality and speed are NOT established.
   This is not connected to the live model or installed in Work/Assistant.
   A reproducible audit confirms the old peer save/restore footprint omits
   most BFP8 staging and the relocated GDN code, so it cannot be reused.
   An experimental receipt checker passes tests against actual simulated
   worker proofs; it cannot authenticate weight addresses by itself.
   A ROOT-compatible converted-address translation now matches the
   independently generated host plan for all 22848 jobs. A separately linked
   RV32 helper matches 1190 jobs in simulation. An explicit experimental
   build now connects it and the receipt checker to the real ROOT source;
   direct compiled-ROOT function tests match 72 planned jobs in simulation.
   The normal BF16 ROOT rebuild is byte-for-byte unchanged. This experimental
   path is NOT installed or fully executed, authenticates neither its table
   nor uploaded pages, and cannot reuse the old native owner/journal.
   A CPU-only hybrid preparation tool now builds for Haiku and can create or
   verify the 1071 BFP4 cache fragments; it has NOT been run on the full
   model. A separate page adapter selects BFP4, existing BFP8 or original
   pages and can preflight all 1344 converted fragments. Its full-coverage
   test uses simulated readers; one BFP4 fragment uses an actual disk-cache
   fixture. The adapter is not linked to a card uploader or Work/Assistant.
   A two-position teacher-forced CPU comparison completed with independently
   retained candidate/original state. Both selected the same token at each
   position; KL was 0.20372 and 0.02355, with top-five overlap 4/5 and 5/5.
   This is not natural answer quality, P100A execution or a speed result.
   See benchmarks/qwen38-hybrid-two-token-cpu-20261107.txt.
   Matched-input diagnostic121 completed physically: on one tensor7/32-row
   band and two passes, Q4 took 643321/643229 cycles and BFP4 took
   227257/227156 cycles, a 2.83x ratio of means. The outputs differed by
   14.34% relative L2. This is NOT full-model speed or answer quality;
   see benchmarks/qwen38-matched-band-physical-20261107.txt.
