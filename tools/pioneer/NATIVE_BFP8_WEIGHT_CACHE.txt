This is a NEW REQUANTIZATION recipe, not the lossless Assistant disk cache.
All supported original Q4_K/Q6_K/Q8_0 matrices become native BFP8_B tiles;
the default mixed converter remains Q4->BFP4,others->BFP8. No running Work,
driver or Assistant selects this alternative. No comparator is relaxed and
the original GGUF bytes remain unchanged. Conversion is CPU preparation of
immutable weights, NOT runtime CPU learned products or inference fallback.

Build in a NEW absolute directory (no install/model/card operation):
  python3 tools/pioneer/build_qwen38_native_weight_cache.py /absolute/new-build --all-bfp8
For Haiku additionally pass --haiku-build /Volumes/HaikuBuildLocal/generated.riscv64.
The resulting binary is pioneer-q38-native-bfp8-weight-cache. It accepts the
same CPU-only --build ORIGINAL NEW_PRIVATE_CACHE [--tensor EXACT_NAME] syntax.
Use a separate dedicated cache, e.g. .p100a-native-bfp8-weights-v2. Do not
launch a full28.6GB conversion without free disk headroom and a qualified
consumer/arena plan. It is NOT installed on the Pioneer by this checkpoint.
Source fingerprint includes the optional converter and explicit recipe choice;
cache key/version/source/recipe isolation prevents interchange with mixed or
lossless entries, even when original Q8/Q6 produce the same payload bytes.
Rebuilding the default converter also changes its source fingerprint, not its
layout; the previously installed CPU utility and existing entries are untouched.

Actual Mac production-utility create and SEPARATE reuse both CLOSED0,stderr0:

Address and throughput constraints (2026-11-04)
----------------------------------------------
The DATA proposal now also excludes the DRAM tile's TOP16MiB register
window. The vendor's pinned Blackhole constant is0xff000000,not4GiB:
https://github.com/tenstorrent/tt-umd/blob/aaed35c594b93d88f8224ea340ae095f3fa80efa/tt-umd/api/tt-umd/arch/blackhole_implementation.hpp
Its DRAM_BANK_SIZE comment distinguishes GDDR from tile registers there.
With64MiB base,the hypothetical cap cannot exceed0xfb000000. The3.75GiB
proposal ends at0xf4000000,below that register window. This is ONLY an
address-class bound,NOT proof of board capacity,free memory,reservation,
routes,alias safety or usable bytes. Current native3GiB/bank stays unchanged.
The pinned Metal descriptor agrees on view size and has firmware-dependent
MRISC endpoint assignments;never replace the Pioneer's firmware-bound routes
merely from a newer generic descriptor:
https://github.com/tenstorrent/tt-metal/blob/f3ef8f22aaa8c499a58229dcca1f26864ac1001e/tt_metal/soc_descriptors/blackhole_140_arch.yaml

Rated p100a memory bandwidth is448GB/s,not an observed speed:
https://docs.tenstorrent.com/aibs/blackhole/index.html
For NAIVE batch1 decode streaming all27231682560B device matrices per token,
448e9/bytes gives16.451426 tokens/s IDEALLY,before compute/state/overhead.
Even optimistically dedicating ALL180MiB SRAM to static weights gives only
16.566247 in that traffic model. These are conditional analytical bounds,
NOT real benchmarks or a universal limit on other dataflows/algorithms.
Thus the20tok/s goal cannot be assumed from all-BFP8 residency alone:lower
weight traffic (e.g. faithful compressed/native4-bit processing),reuse or a
separately qualified decoding algorithm remains necessary. No automatic
lower-precision recipe,relaxed reference,CPU fallback or target change is
authorized by this calculation. Full-model quality/performance still required.
