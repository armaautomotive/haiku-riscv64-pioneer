P100A / Qwen 27B: compact milestones and work inventory
=======================================================
November 7, 2026. This is a navigation aid, not evidence of a new benchmark.
Keep the full objective: usable self-hosted inference on the P100A, targeting
20 tokens/second, with no CPU-reference inference in Work. Validation remains
separate; preserve the working system and do not discard existing work.

Baseline: one short full-27B request executed inference on the card at about
0.1729 tokens/second, with about 35 minutes from Generate to answer-ready.
The response was a truncated counting example, not broad quality validation.
The 20-token/second target is unproven. Evidence:
benchmarks/qwen38-fast-decode-profile-physical-20261106.txt and
benchmarks/qwen38-early-job-snapshot-physical-20261106.txt.

Use the unchanged vector92 result as the comparison baseline: the prompt is
"Count from 1 to 50, one number per line. Do not add explanations." It used
31 prompt tokens, up to 32 output tokens and a 31-step post-prompt count
window. The archived rate is 0.172813448..0.172816755 tokens/second; its
range describes timestamp observation, not run-to-run variation. To check
the archived complete transcript without touching the Pioneer, run from the
repository root:

python3 tools/pioneer/tests/parse_pioneer_q38_full_offload_rate_log.py tools/pioneer/benchmarks/qwen38-vector-q4-full-card-20261104/rate.stdout tools/pioneer/benchmarks/qwen38-vector-q4-full-card-20261104/rate.stderr

This checks the recorded transcript, not a new hardware run or a model-quality
test. The original test stage is spent and must never be replayed. A future
candidate comparison needs a new independently qualified stage, matching
prompt, model, token limit and measurement window, plus clean recovery.

Milestone 2: make a go/no-go decision on one candidate
-----------------------------------------------------
Candidate: converted BFP4/BFP8 FFN weights and native card operations. A
single BFP4 band took roughly 227k card cycles including GDDR and compute,
versus roughly 643k in a prior Q4 diagnostic, but inputs and representations
are not an equivalent-accuracy paired benchmark. Whole-model quality is not
established; one-token hybrid quality tests are warnings, not a pass.
A two-position fixed-token CPU comparison retained separate original and
candidate state and matched the top token on each position; this is still
not a natural-prompt or broad model-quality pass. See
benchmarks/qwen38-hybrid-two-token-cpu-20261107.txt.
Source inspection also confirms the recorded Q4 and BFP4 timing runs did not
use the same input vector: the Q4 exporter uses a (column*19 + block*11)
pattern, while the BFP4 exporter uses an (input*13) pattern. Thus even their
input data are not paired; do not quote their cycle ratio as an A/B speedup.
See pioneer_native_compact_q4_stream_export.cpp and
pioneer_bfp4_real_band_export.cpp for the exact BF16 encodings.
One matched-input BFP4 CPU prediction for the first band now differs from
the archived Q4 card output by 0.14342 relative L2 (32 values). This is a
quality warning, not a full-model verdict or a BFP4 card timing. See
benchmarks/qwen38-matched-band-preparation-20261107.txt.
The corresponding matched BFP4 band subsequently ran on the P100A: its two
passes took 227257/227156 cycles versus the archived Q4's 643321/643229,
with the same 0.14342 relative L2 output difference. This demonstrates a
faster operation on one band, NOT a full-model speed or quality pass. See
benchmarks/qwen38-matched-band-physical-20261107.txt.

Current work: a three-position CPU-only hybrid comparison finished with the
same greedy choice as the original at all three positions. That single raw
prefix is not a generated answer or broad quality pass; see
benchmarks/qwen38-hybrid-hello-three-cpu-20261107.txt. Both BFP4 and BFP8
disk caches finished successfully; their combined read-only preflight is
running. None is an on-card full-model speed result. The preflight must pass
before the prepared caches can be considered for use in a device test.

Before further full-model integration, define a model-relevant accuracy gate,
measure representative real weights and prompts against the Q4 reference,
and establish a matched on-card operation comparison including data movement.
Report the results and accept, improve, or abandon the candidate. Avoid
claiming model speed from band cycles or treating cache preparation as a gain.
Relevant evidence: benchmarks/qwen38-bfp4-dram-real-band-physical-20261106.txt
and benchmarks/qwen38-bfp-hybrid-cpu-quality-20261106.txt.

Milestone 3: prove full-model improvement
-----------------------------------------
Only after the candidate passes its gate, connect it safely to the real
model and compare matched full-27B requests, including correctness, generation
tokens/second, loading time, repeatability and safe driver restoration.
An isolated operation or a successful build does not complete this milestone.

Milestone 4: usable Assistant
-----------------------------
Keep a qualified model loaded across requests, expose the proven Work mode in
Assistant, verify load/unload and real use, and measure warm response latency.
Do not replace the working Assistant with an unqualified experiment.

At each milestone report: change, test scope, measured result, quality limits,
decision, and next action. More detailed history remains in P100A_WORK_PLAN.txt,
P100A_CURRENT_STATUS.txt and benchmarks/. Do not delete the evidence.
