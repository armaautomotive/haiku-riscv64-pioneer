Performance constraint,not a prediction
--------------------------------------
This version spends MORE on-card scalar instructions converting original
weights and repeating BF16 inputs. For example,K5120/groups16/two jobs:
accepted control5522145 versus new44090461 executed RV instructions.
K17408/groups16:18429537 versus149547997. These are EMULATOR instruction
counts,NOT physical time,tokens/sec or a predicted slowdown/speedup.
They are a reason NOT to promote this as the fast driver without work
on its data path. No claim is made that three FPU products are faster
than the old two integer-overlay matrix operations.

Next performance work must remove repeated conversion,not add UI or
another unchanged fixed diagnostic. Use the already lossless native
primary+escape format in the prepared weights/source path,within the
EXISTING measured seven source-bank caps;dense masks exceed those caps,
so the measured sparse-mask/index allocation is required. Preserve exact
original metadata and rounding. Reuse activation conversion safely.
Then qualify the actual complete native worker/USER pair and measure the
same public real27B request before claiming a performance improvement.
