Hybrid125 recovery: changed on-disk records
==========================================
After a single OFF, settle, single ON, verified Linux host fingerprint, and
fresh 64-CPU/full-memory Haiku boot, the existing reviewed one-shot recovery
helper refused before changing the installed driver. It found that the
on-disk state, trial.stdout, trial.stderr and trial.exit no longer matched
the four recorded pre-power hashes. The preserved pre-power Mac copies still
match every recorded SHA-256, including parent.stdout. Parent.stdout on the
Haiku volume also no longer matches. The exact one-shot trial marker remains
in place. No failed trial was rerun, and no card computation was issued.

Read-only analysis of the copied post-boot records found state equals 41
bytes at offset 69632 of the already present stable.backup, trial.stderr
equals 38 bytes at offset 65536, and the entire 4704-byte trial.stdout equals
the first 4704 bytes of that backup. Two-byte trial.exit also appears in that
binary but is too short to identify its origin. Parent.stdout begins with
25 bytes found in the saved run.sh; it is not a full match. A local postboot
copy is in /private/tmp/pioneer-hybrid125-after-20261107-a and the pre-power
copy is in /private/tmp/pioneer-hybrid125-failed.h6FLuiMP. Temporary copies
are not archival backups. None of this proves the cause; stale file data,
cache/flush problems, wrong block mapping and other explanations remain open.

The preserved trial wrapper was also inspected: it ran sync during driver
exchange, but its failure trap and the final writes of state/trial stdout,
stderr and exit status did not explicitly flush those files. A missing final
flush is consistent with stale data after a forced power-off, but this alone
does not establish whether a later external sync occurred or prove the cause.
Future trial wrappers need explicit checked durability before power cycling.

The BFS inode maps were read without mutation. The affected state, stderr and
stdout data occupy group118 blocks 3694, 3692 and 3660-3662 respectively;
stable.backup occupies 118:65124-65475 and 119:62946-63112. Thus their
recorded allocations do not overlap. Reads via the Haiku block-device path
of state block 7736942 and backup block 7798406 produced identical SHA-256
for the first 41 bytes; stderr block 7736940 and backup block 7798404 matched
for the first 38; stdout block 7736908 and backup block 7798372 matched for
2048 bytes. These are device-path reads through the running OS, not an
independent offline disk image; caching or storage I/O issues remain possible.

The Haiku host key matched the previously recorded fingerprint. A read-only
checkfs --check-only /boot completed twice. The filtered second run reported
58178 nodes, zero missing allocated blocks, zero multiply allocated blocks,
and 39436 blocks that could be freed (2048 bytes per block, about 77 MiB).
These allocation findings do not establish file-content integrity or the
reason for the stale data; open/deleted files and concurrent activity can
also affect accounting. No repair was requested or executed. Filtered BFS,
journal and I/O error searches of the current system log yielded no lines.

Driver125 and the stable041 binary separately matched their pinned hashes.
The complete 18,973,870,528-byte Qwen3.8-27B-Q4_K_M.gguf was read on the
running Haiku system and its SHA-256 matched the previously pinned
c600de0300ae8a0eb3a6c0b8b5561b8b96f16bd2c863c2a66c42de29d391a747.
This verifies that one file's contents on that read, not other files or the
future durability of writes.
Fresh boot CPU-only reload metadata reported tag125/generation1/cold0/owner0.
This is not proof of full storage safety or authorization to weaken the
guard. The installed driver remains tag125 and no accelerator experiment is
authorized by these observations. Investigate persistence and protect the
filesystem before any new restore or physical inference trial.

Whole-allocation-block follow-up on the same pinned Linux boot
-------------------------------------------------------------
The read-only evidence program was extended to read every full 2048-byte
allocated block for the three affected files and search the entire verified
stable.backup for exact matches. The same device serial, partition geometry,
unmounted state, inode sizes and allocation runs were rechecked before the
reads. No raw contents were printed, including data beyond logical file EOF.
Each block matched exactly once in the backup:

 state         block 7736942 -> backup offset 69632
 trial.stderr  block 7736940 -> backup offset 65536
 trial.stdout  block 7736908 -> backup offset 0
 trial.stdout  block 7736909 -> backup offset 2048
 trial.stdout  block 7736910 -> backup offset 4096

This strengthens the evidence that whole old backup blocks are present at
the affected allocation locations, including beyond those files' logical
ends. It does not establish whether this came from stale reused blocks,
misdirected writes, cache or controller behavior, or another cause; it also
does not establish general volume or power-loss safety. The guard remains
unchanged and no card, filesystem repair, driver exchange or writes to the
Haiku partition were performed.

Linux reports the SATA device's write cache as "write back" and queue FUA
capability as 0. A read-only SMART query reported overall health PASSED;
reallocated sectors, uncorrectable errors and interface CRC errors each
reported zero. These indicators do not rule out a flush, power-loss,
controller, filesystem or other data-integrity problem. Keep the existing
recovery guard intact; the backup hash alone does not resolve the anomaly.

Aligned old-driver extent comparison
------------------------------------
The raw Linux evidence helper was extended with an explicit pinned hash for
stable.backup and a bounded, read-only comparison. It rechecked the same disk,
unmounted BFS partition, geometry and four recorded inode maps, then compared
518 complete 2048-byte blocks starting at physical partition block 7736908
against corresponding offsets in stable.backup. It printed only match ranges,
not disk contents. Half-open ranges [0,35) and [36,160) matched exactly;
the affected stdout blocks are indices 0-2, stderr index 32 and state index
34. The single mismatching index 35 and remaining indices 160-517 did not
match; no inference is made about their ownership or contents.

This is substantially stronger evidence for a contiguous remnant of an old
copy of the driver at these physical locations, not merely coincidental
individual block matches. The trial did replace an installed driver whose
content had the same pinned hash before creating the trial output files, so
reallocation of blocks formerly holding that driver followed by loss of
unflushed new file data is plausible. There is no pre-replacement allocation
map to establish that history; misdirected writes, cache behavior, journal
ordering and other causes are not excluded. This is not proof of a filesystem
failure mode, power-loss safety, a fresh power epoch, or permission to relax
the restoration guard. No block was modified and no GPU operation was issued.

Linux BeFS model-read limitation
--------------------------------
The same Linux boot mounted the identified /dev/sda1 BeFS volume with
ro,nosuid,nodev,noexec to assess use of the real model without writing Haiku.
It reported the expected model file size, 18973870528 bytes, but a sequential
read returned only 2147483648 bytes. Reads at 2047 MiB returned a full MiB;
at 2048 MiB they returned EOF, and larger seeks could not reach the requested
offset. Linux sha256sum nevertheless returned success and printed
3b058ab0c1a0db9926f57910f0614297f177a66347458deb1216571b229af6a8: this
is a hash of the truncated stream, NOT a valid hash of the stated file size.

The local 18973870528-byte copy at generated.pioneer/models has full SHA-256
c600de0300ae8a0eb3a6c0b8b5561b8b96f16bd2c863c2a66c42de29d391a747; its
first exactly 2147483648 bytes hash to the same 3b058a... value. The Linux
view's first MiB matched the corresponding local MiB. This explains the
initial whole-file hash discrepancy as a short Linux read; it does NOT prove
that the unread remainder on the Haiku disk is intact, or that BeFS on this
Linux build can verify large files. Small stable.backup and state hashes
matched the earlier Linux raw-block observations. The partition was then
unmounted and findmnt no longer listed it. No Haiku write, GPU operation,
repair, replacement or power action was performed.
