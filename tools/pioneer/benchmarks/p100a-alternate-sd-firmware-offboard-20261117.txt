P100A new-slot firmware test: booted, no P100A endpoint
======================================================
November 17, 2026. Both PCIe cards stayed in place for all tests.
The old firmware boot trace shows SG2042 ZSBL v0.2 and OpenSBI v1.2
(2023-08-30 build). The live device tree and both installed Pioneer DTBs
have identical pcie-id, link-id, linux,pci-domain, bus-range, reg, ranges
and dma-ranges on all four roots. The affected 7060000000.pcie root is
controller 0/link 0/domain 0. Selecting either installed DTB would not
change those properties. The physical PCB revision is still unverified.

Alternate boot components
-------------------------
RevyOS publishes a single-socket Pioneer firmware image for microSD:
https://docs.revyos.dev/docs/Installation/milkv-pioneer/
https://mirror.iscas.ac.cn/revyos/extra/images/sg2042/20251226/

The exact 268435456-byte firmware_sg2042-single-revyos_6.18.y-sg204x-v1.7.img
matched the mirror's SHA-256:
20b0e2db84a1a52aa37ad3cc155ee55206384c2f81da1a1e0cd88d8c1389adaf
The package has a different ZSBL from the earlier Fedora rescue SD, a
different LinuxBoot kernel, and a Milk-V Pioneer DTB that describes the
affected root as sophgo,sg2042-pcie-host rather than sophgo,cdns-pcie-host.
Its root 0 register/range/bus values differ. This is a meaningful firmware
comparison, not a demonstrated P100A fix. Neither that DTB nor any part of
the package should be used with the current Haiku boot helper by itself.

Diagnostic image and gates
--------------------------
The stock initramfs selects another operating system. The diagnostic copy
has only one init executable, a console node and a sysfs mount point in
its initramfs. PID 1 mounts sysfs read-only, inventories PCI devices, prints
the root-port and Blackhole link data if available, and parks. It does not
run an installer, launch an installed OS, open a block device, load a
driver, write PCI sysfs, use the network, or issue a MTD write. Vendor
firmware and the kernel still perform their normal boot and enumeration.

Tools: cross GCC/ld for RISC-V, Python 3 and mtools. Build from the repo:

  CC=/absolute/path/to/riscv64-unknown-haiku-gcc
  "$CC" -std=c11 -Os -Wall -Wextra -Werror -ffreestanding -fno-builtin \
    -fno-stack-protector -msmall-data-limit=0 -fno-pic -fno-pie \
    -c tools/pioneer/pioneer_pcie_sd_probe.c -o probe-init.o
  "$("$CC" -print-prog-name=ld)" --no-relax -static -e _start \
    -o probe-init probe-init.o
  python3 tools/pioneer/make_pioneer_pcie_sd_probe.py \
    stock-firmware.img probe-init new-diagnostic.img

The builder only creates a new ordinary image file. It pins the vendor
image, verifies the Linux RV64 ELF shape, and reads back the new initramfs.
Readback confirmed all seven remaining firmware files, the partition table
and pre-partition data unchanged. Independent archive inspection found
only the four intended entries (including dev/console 5:1); the init ELF
matched byte-for-byte. Existing output, unrelated image and non-ELF
refusals passed.

The final init ELF was run natively under Fedora in a private mount/PID
namespace and a minimal temporary root, with a three-second outer bound.
Outside PID 1 it exited 2 without mounting. As PID 1 its independently
observed output included 0000:00:00.0, 0002:81:00.0,
P100A_NOT_ENUMERATED and PIONEER_PCIE_SD_PROBE_PARKED. It finished only
when the disposable test namespace was killed. No reboot or hardware
change occurred in that test. This exercises the binary and inventory,
not the RevyOS kernel or anything booted from actual SD media.

Physical trial requires a separately approved SD target, no reuse of either
existing recovery or Haiku card, controlled power-off before insertion,
and serial proof of the alternate firmware/kernel followed by the probe
banner and terminal result. Do not interpret a fallback Fedora boot or
missing probe output as absence of the P100A under the alternate firmware.
If it enumerates, collect the actual topology before rebuilding Haiku's
guards. No SPI/NVMe write or new inference benchmark occurred.

Diagnostic SD readback
----------------------
The first whole-image readback after imaging the separate spare SD
(serial 0xf891) did not match, so the writer stopped without ejecting.
A second read-only 268435456-byte capture on the Mac had SHA-256
0362f73bbf93b5d9e4897d528d2ac8805b0048872b686313bfd19a78bd4c8956.
The exact MBR, pre-partition space, all eight reserved FAT16 sectors and
all eight boot payloads were unchanged. The independently verified FAT16
structure passed `fsck_msdos -n`. A sector audit attributed every changed
byte to macOS metadata: 48 data sectors in 10 newly allocated clusters
of .Spotlight-V100 and .fseventsd, both mirrored FAT sectors assigning
those previously free clusters, and one root directory sector containing
the two new entries and a volume-label timestamp update. The existing
boot directory entries, allocations and data sectors are unchanged.
Reproduce with `audit_pioneer_pcie_sd_readback.py` against the pinned
reviewed image and raw capture. The exact spare SD was safely ejected
after verification; neither existing recovery card was used.

Physical boot (verified alternate SD)
-------------------------------------
The first ON pulse occurred before the card was physically inserted; that
capture identified the old SPI ZSBL and Fedora 6.1.31 on NVMe. Linux was
shut down cleanly, then the user inserted the verified diagnostic card.
The next single ON pulse gave the following new UART evidence (separate
capture, beginning at byte offset 117415454 in the zero-indexed raw log):

  SOPHGO ZSBL v2.1.2 SG2042
  OpenSBI v1.7
  Linux version 6.18.2-g4a086bd11b15
  sg2042-pcie 7060000000.pcie: Link up
  sg2042-pcie 7060000000.pcie: PCI host bridge to bus 0000:00
  pci 0000:00:00.0: [1f1c:2042] type 01 class 0x060400 PCIe Root Port
  pci 0000:00:00.0: PCI bridge to [bus 01]
  pci 0002:01:00.0: [1002:6779] type 00 class 0x030000 PCIe Legacy Endpoint
  PIONEER_PCIE_SD_PROBE_BEGIN v1
  PCIE_DEVICE 0000:00:00.0 0x1f1c:0x2042
  PCIE_DEVICE 0002:01:00.0 0x1002:0x6779
  P100A_NOT_ENUMERATED
  PIONEER_PCIE_SD_PROBE_PARKED; NO_INSTALLED_OS_STARTED

The complete inventory included 19 PCI functions. Domain 0000 contained
only its root port; no 1e52 vendor or b140 endpoint occurred on any domain.
`Link up` is the host-controller driver's condition before PCI enumeration,
not evidence of a responding Blackhole or its negotiated speed. RevyOS's
alternate firmware/kernel did not restore enumeration. This does not prove
card failure or identify whether reset, power, lane/link or configuration
transactions prevented discovery. No installed OS, benchmark, or driver
ran the P100A. After the probe parked, one seven-second front-panel OFF
hold completed; do not repeat it to confirm power state.
