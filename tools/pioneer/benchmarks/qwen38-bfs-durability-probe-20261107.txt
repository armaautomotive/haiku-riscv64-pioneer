Qwen hybrid recovery: bounded BFS persistence probe
===================================================
November 7, 2026. The prior tag125 recovery guard remains intact and the
failed trial was neither altered nor retried. Before any new card trial,
investigate the stale post-power-cycle trial records described in
qwen38-hybrid125-postboot-file-integrity-20261107.txt.

The current Haiku boot volume reports BFS device /dev/disk/scsi/0/3/0/0,
2048-byte filesystem blocks; it is not the NVMe device path. This is a
SCSI-presented device and does not by itself identify the physical transport.
Source inspection found that BFS fsync calls Inode::Sync and file_cache_sync;
the VFS common_sync path does not itself issue B_FLUSH_DRIVE_CACHE. The
global sync path requests a device flush but discards that ioctl result.
BFS journal flushes also request a device flush and discard its result.
These facts are not proof that lack of a flush caused the old failure.

The separately built pioneer_bfs_durability_probe.cpp creates only a fresh,
private /boot/home/pioneer-bfs-durability-XXXXXX directory and four small
deterministic files. It checks file writes and fsync, invokes global sync
(which has no useful return value), then checks the result of an explicit
B_FLUSH_DRIVE_CACHE ioctl on the exact expected boot device and reads the
files back. Its verify operation is read-only and refuses changed contents,
unexpected device, mode or path. It does not touch the GPU, trial, driver,
other existing files, SD cards or raw disk writes. Host-only fake-flush tests
check invalid-device/path/content/mode/symlink and simulated-flush-failure
refusals; the cross-compiled Haiku binary was SHA-256
99c9914460f8d5a68c92b7b1ffa28b22205585d11be6715e46156995ccac54af.

On the pinned Haiku SSH connection the exact device was verified and the
real checked flush returned success. The created stage remains at
/boot/home/pioneer-bfs-durability-w9D6AH. An independent immediate verify
and SHA-256 reads reported the following; byte counts are 41, 38, 4704 and
131072, respectively:

The read-only BFS inode records named separate direct allocation runs in
group 59, starting at blocks 694, 695, 696 and 699; their lengths were 1, 1,
3 and 64 blocks. Given the observed 16-bit allocation-group shift, read-only
device-path reads from absolute partition blocks 3867318, 3867319, 3867320
and 3867323, truncated to the respective file lengths, gave the same four
hashes. These are reads through the running OS and do not independently
exclude caching, drive faults, incorrect device acknowledgments, or other
file corruption. The checked ioctl returned success; at that point no
post-reboot check had run. A later check can establish only these four files
in that one trial, not whole-volume or power-loss safety.

Follow-up: one normal Haiku `shutdown -rs` produced a fresh firmware/Linux
boot; no relay pulse or physical power-off was used. On the pinned Linux
connection, boot ID 04c4ac9a-71f1-483c-8ab4-573c5bb69333, disk serial
S14CNSAD300075H, BFS UUID 020147de08752551 and partition start 64 matched
the recorded system. The Haiku partition was unmounted. Linux read its
four inode allocation records and the same four raw partition block ranges;
all four SHA-256 hashes above matched the pre-reboot values. This is an
independent OS after an ordinary restart, not a forced-off or mains-loss
test. Haiku was then restored using the pinned 64-CPU, 128-GiB untimed
SD-free helper, without a journal-recovery override, and its pinned SSH
reported a successful file-level verify:

 /boot/home/pioneer-bfs-durability-probe-20261107-b --verify /boot/home/pioneer-bfs-durability-w9D6AH /dev/disk/scsi/0/3/0/0

Haiku reported 64 CPUs and 137034936320 maximum memory bytes; app_server,
Tracker, Deskbar and input_server were running (desktop visibility/input were
not independently checked). The four previously altered failed-trial records
had the same hashes as the preserved first post-failure copies, not the
original pre-power hashes. CPU-only metadata still reported driver
tag2026110700010125, generation1, cold0 and active_owner0. Haiku's shutdown
serial included BFS index-lookup warnings; their cause is not established.

This success covers four files and one orderly restart, not sudden power
loss, the previous failure's cause, the filesystem as a whole, or later
write durability. The probe does not attest that a reboot occurred. No card
operation, recovery guard bypass or repair was performed. Do not interpret
this result as authorization to discard failed-trial evidence, weaken the
restoration guard, install a new driver or rerun the spent trial.

Follow-up after 12 TB disk installation
--------------------------------------
Following the later Linux shutdown, physical disk installation and fresh
Linux-to-Haiku boot, the pinned probe binary still hashed to 99c99144... and
its read-only --verify again reported that all four test files matched. This
adds another post-restart observation; the precise PSU-power history was not
independently attested, and it is not a test of abrupt power loss immediately
after a checked flush or of other files. The same old trial state/stdout/
stderr/exit still had the previously documented altered hashes; the installed
125 driver and stable.backup retained their respective pinned hashes. The
recovery guard was not changed, and no P100A operation was issued.
