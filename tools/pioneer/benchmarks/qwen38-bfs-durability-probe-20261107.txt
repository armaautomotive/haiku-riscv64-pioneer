Qwen hybrid recovery: bounded BFS persistence probe
===================================================
November 7, 2026. The prior tag125 recovery guard remains intact and the
failed trial was neither altered nor retried. Before any new card trial,
investigate the stale post-power-cycle trial records described in
qwen38-hybrid125-postboot-file-integrity-20261107.txt.

The current Haiku boot volume reports BFS device /dev/disk/scsi/0/3/0/0,
2048-byte filesystem blocks; it is not the NVMe device path. This is a
SCSI-presented device and does not by itself identify the physical transport.
Source inspection found that BFS fsync calls Inode::Sync and file_cache_sync;
the VFS common_sync path does not itself issue B_FLUSH_DRIVE_CACHE. The
global sync path requests a device flush but discards that ioctl result.
BFS journal flushes also request a device flush and discard its result.
These facts are not proof that lack of a flush caused the old failure.

The separately built pioneer_bfs_durability_probe.cpp creates only a fresh,
private /boot/home/pioneer-bfs-durability-XXXXXX directory and four small
deterministic files. It checks file writes and fsync, invokes global sync
(which has no useful return value), then checks the result of an explicit
B_FLUSH_DRIVE_CACHE ioctl on the exact expected boot device and reads the
files back. Its verify operation is read-only and refuses changed contents,
unexpected device, mode or path. It does not touch the GPU, trial, driver,
other existing files, SD cards or raw disk writes. Host-only fake-flush tests
check invalid-device/path/content/mode/symlink and simulated-flush-failure
refusals; the cross-compiled Haiku binary was SHA-256
99c9914460f8d5a68c92b7b1ffa28b22205585d11be6715e46156995ccac54af.
