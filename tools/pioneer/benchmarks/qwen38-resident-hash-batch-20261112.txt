Resident page-hash batch experiment, 2026-11-12

The span-upload service records the existing non-cryptographic per-page FNV
hash after a successful transfer. Its hash definition, per-page publication
order, ownership checks, upload proof and Work/strict distinction are not
changed. The candidate interleaves four independent 4 KiB page hashes, with
the existing scalar hash for trailing pages. This is a loading-path change,
not an inference-kernel or quality change.

After the protected P100A benchmark had closed, the standalone CPU-only
candidate was copied to the Pioneer and SHA-256 checked:
a7852d232cd6153e092878a82ab94e2e9bc9eae8c97019f55389f2fdf57f9797.
It produced the original exact hashes for 512 synthetic pages. Three
64 MiB cache-hot synthetic runs, scalar first each time, measured respectively
226734000/90458000, 168410000/90476000 and 168418000/90494000 ns
for scalar/four-page hashing. These are CPU microbenchmarks with a 16 KiB
working set, not a model upload, accelerator bandwidth or tokens/sec result;
order and caching effects are not controlled. No device was accessed.

The integrated implementation was then checked against the original hash
under ASan/UBSan; strict and separate Work-mode actual span-service mocks
passed, including 1, 2, 3, 4, 5, 6, 7 and 256-page requests, exact hash
publication, refusal and cleanup paths. The resident-store tests passed.
The separate QGWD tracked-receipt span simulation also passed in strict and
fast modes, including ordering and quarantine checks.
The first offline hot-reload build (9b8bd313...) did NOT enable the span
feature, so it did not exercise this implementation and is not an appropriate
test driver. Subsequent clean source archives, excluding unrelated working-tree
edits, were built with the full scale-reuse and fast-span selectors. The
pre-change baseline produced driver SHA-256
68105500213f503811bf1b73473b08a01bb4b04b78d037817a809d6828b66548;
the hash-batched source produced
e37af32ff9d0984da8302da8b4883683727de3dad00ddfb142135cda64227797.
Both used tag 2026102100010012, but that rebuilt baseline did NOT match the
installed stable driver, so neither build is qualified for installation.

Follow-up source isolation: a clean archive of historical commit e56d7dab7d,
with the full scale-reuse/fast-span settings AND the previously omitted
local-delta-probe setting, reproduced the installed baseline byte-for-byte:
041fef189829c58791a7e4a86e2b15b182fa1a6c9cc9f03a91037ba15b353403.
Applying only the same hash interleaving to that historical source and using
the distinct candidate tag 2026111200010002 produced
3be6fe0bbfe7574d4cd3fd774e6d914497bc4cb9df19c31220e1afcfef998389;
the guard and default control remained d1ce2aa4... and 2df0e0f8... . Strict
and Work span-service simulations also passed against this historical source.
These are offline builds and tests; the candidate has not been installed or
run on the card. A controlled hardware trial and restoration are still owed.
No complete model load comparison or end-to-end speedup claim is made.

Bounded synthetic hardware comparison: the parent ran once on the Pioneer,
first using the installed 041fef18... baseline, then the distinct candidate,
then restored 041fef18... . Both Work-transport trials returned success and
explicitly closed; each transferred 7,512,064 synthetic bytes in 21 jobs and
the separate debug client compared every resulting byte. Summed upload-call
times were 0.961976 seconds baseline and 0.942908 seconds candidate. This
single baseline-then-candidate pair is not enough to establish a speedup;
timings include software and transport work and are not raw PCIe bandwidth.
The test did not load a model or measure inference. Both stderr files were
empty and the parent actually exited 0 with CLOSED_STABLE_RESTORED.
