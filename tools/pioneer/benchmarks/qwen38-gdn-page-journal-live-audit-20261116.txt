Next engineering gate
---------------------
The candidate is not ready to install. Under its candidate macro, native
startup still invokes `PioneerQ38TokenStartupPlan::Build(...)` without the
`redistributedGdn=true` argument, so the scattered page allocator/map is not
selected for that token. Even after selecting the map, the
97,484,800-byte page journal is not instantiated or bound to the native
session. Correct integration must preserve every page's arbitrary preexisting
data across launch, commit/replay the cache only at the outer model-token
boundary, and restore on every successful close without exposing partial
state after failure. The ordinary `RestoreOriginalL1` deadline is 300 s
(`system_time()` counts microseconds); there is no measured bound for this
larger page journal. It needs bounded/batched transport and explicit
fault-retention semantics before hardware testing.

The live machine has 64 CPUs and full RAM with stable041 restored. No current
all-card Qwen request has returned a valid speed result. Last qualified
full-Q4 result remains approximately 0.1728 tokens/sec; 20 tokens/sec remains
unmet.

Tag206 lifecycle integration checkpoint, later November 16
---------------------------------------------------------
The native candidate now passes `redistributedGdn=true` only under the
tag206 page-access role. `PioneerQ38TokenMemory::PrepareHeld` captures the
97,484,800-byte scattered-page original journal after its own complete held
image readback and before the first firmware write. Its page adapter checks
all 120 held workers once before capture, then uses the exact allocator-owned
worker/page accessors for each page. After committed output is drained and
the root is held, the token owner restores the page journal first, while the
launched journal still authorizes access; the existing `RestoreOriginalL1`
step follows unchanged. The separate page restore adapter was intended to
have a 15-second budget, but the literal used the wrong units (see below).
Any interrupted capture/restore keeps the snapshot
and faults/quarantines the native owner. A prepared session closed before
launch discards its untouched snapshot. The tag206 role still excludes Work
and CPU-reference modes.

Restore timeout correction, November 17
---------------------------------------
The deployed diagnostic tag206 used `15,000,000,000` as a delta from
`Q38CohortNow()`, which returns Haiku `system_time()` in microseconds. The
configured limit was 15,000 s, not 15 s. The checked-in candidate now uses
an explicit 300,000,000 us cap, matching the ordinary L1 restore limit;
15 s has not been shown adequate for this 97,484,800-byte journal's writes
and two readback passes. It also refuses a backward clock even when it is
still above the start, and checks the deadline after each completed page
I/O, including the final verification read. If a page overruns the limit,
the existing owner retains the snapshot and quarantines the card; the
journal does not retry or request more device operations. The guard does
not preempt an individual in-flight hardware access.

Sanitized journal tests cover the exact microsecond boundary, backward and
wrapped clocks, a timeout after the first verification read, and a timeout
during the last verification read. Both restore timeouts kept the snapshot
and refused any second restore. These are synthetic tests. No new image was
put on the Pioneer; the running one-shot still uses the original pinned
binary. A measured restore duration is still required.

The main-tree build refused its pinned default-driver digest. The default
translation unit does not include either changed timeout header; its
dependency list changed with the November 17 PCIe BAR probe work. No
checksum gate was changed. An isolated build from tracked sources restored
only BlackholePioneerMmioProbe.h to the original-slot version immediately
before 81be24c0c2 and overlaid the two timeout headers. It reproduced the
exact default digest listed above, passed all 43 role refusals, and built
candidate SHA-256
`24a1fef4e51dfcd901688bd32c0d7d05f5d5553797572286df2baaec1fb23439`.
This is build-only evidence for the original-slot baseline. The candidate
is a different binary from the running one even though the tag is the same;
do not substitute it in an existing one-shot stage.

Ordinary held L1 journal: batched-read inspection
-------------------------------------------------
After completing the prepared weight upload, the live tag206 worker's
Haiku thread continued increasing kernel CPU time at roughly wall time
with unchanged user CPU time, without the explicit post-START marker.
This does not identify its exact subphase or prove any device progress.

The original routed-token inspection fixture saves 11,528,762 words
(46,115,048 bytes) and rereads each one before installing firmware. The
actual prepared-Q4 native driver instead selects the QTP3 footprint
with 13,480,506 words (53,922,024 bytes). Both are separate from the
97,484,800-byte scattered-state journal. Each original ordinary-journal
word in the live tag206 takes the scalar checked IO path.
`PioneerQ38HeldSnapshotBatch.h` groups the same visitation order only
within an existing L1 span and one existing uncached aperture, at most
128 32-bit reads per group. The boot instruction and special tail view
are preserved as scalar operations. A batch has a scope check before and
after the reads and does not publish any new saved words on failure.

The exhaustive ASan/UBSan tests compared all 120 workers' addresses
and returned values to the legacy per-word traversal in both layouts.
Per pass, the native geometry produced 105,309 mapped batches plus
1,080 scalar exceptions (the routed fixture produced 90,061+1,080).
Both original-data passes and the number/type of 32-bit loads remain
unchanged. Mixed apertures, an unmapped address, invalid bounds, and
pre-read, mid-load and late-scope faults were refused. These are source
and fixture counts, not measured PCIe traffic or time.

Native tag209 wires the helper only into the two startup capture passes
under the already-held preparation call. It independently verifies that
the exact worker, owner and mapping remain live around each group. It
uses the legacy path for the boot/tail views, and does not change code
install, cancellation, rollback, restore, or model execution. This is a
startup optimization, not a hypothesis about per-token GPU speed or the
cause of the tag206 fault. The original-slot isolated Haiku build passed
46 refusal checks, matched all 15 firmware arrays, kept the default
driver hash unchanged and emitted native driver SHA256
`350bd33d543b142ab5b0f58e71c8209b7cd57fb8678d9f35b2b04362c4254cf3`.
An isolated rebuild without the new selector reproduced the prior
`24a1fef4…` tag206 restore-budget control byte-for-byte. The tag209
driver is neither installed nor physically qualified.
