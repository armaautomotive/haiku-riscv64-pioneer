# ASIC timer reset qualification, 2026-11-25

The restricted, empty-session qualification was attempted once on Haiku after the stable driver reported generation 1, no active owner and no cold latch; no 27B process or project lock was present. Both project locks were acquired. The candidate driver (tag `2026112500030024`, SHA-256 `b660bb61458cf566c574c1bc4c3c2cd96606b4f16bd8e373e05cb16f14db5fcd`) loaded as generation 2. No model inference or worker start was attempted.

The reset timed out at recovery stage 2, detail 6. The four logged attempts consist of the initial request and bounded resume polls; the implementation retains the original reset ticket and does not issue the timer trigger again while polling. Root trace samples 0 and 6 were clean; samples 5 and 7 recorded device status `0x0006` and uncorrectable status `0x00000001`. This does not identify the cause or prove link stability at any particular endpoint access. Full client output is in `qualify.stderr`. The client reported `reset_completed=0`; the candidate and stable backup remained in place with both locks, and Haiku remained reachable. This is a failed recovery test, not proof of no-reboot recovery, inference, valid model output or throughput.

Before the live test the script paths for success, pre-reset rejection, retained failure, post-boot restoration and lock handling passed on a mock host. The root-first check prevents reads when a root sample is already unhealthy; it does not guarantee link continuity or exclude all other PCI clients. Do not repeat this reset without diagnosing the captured error and addressing the missing controller-wide exclusion.

After a single authorized OFF pulse, a shutdown interval and a single ON pulse, the machine booted Linux from the existing NVMe setup. The pinned 64-CPU Haiku helper and image were hash-verified and booted. The restoration script checked host health and fresh candidate generation 1, loaded the stable driver and released both locks. An independent postflight reported stable driver55 generation 2 with `quiesced0 cold0 active_owner0`, the stable driver hash `041fef189829c58791a7e4a86e2b15b182fa1a6c9cc9f03a91037ba15b353403`, absent project locks and no diagnostic process. The 4B and 27B files remained at their recorded sizes; they were not freshly hashed. This was recovery after a power cycle, not in-place recovery.
