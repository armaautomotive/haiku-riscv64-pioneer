Qwen 27B: on-card recurrent and attention timing diagnostic
=========================================================

The measured vector92 v3 run grouped 21.26% of decode-body cycles into
recurrent work outside its projections, and 12.41% into dense work outside
its projections. Neither bucket identifies where the card actually spends
that time. The separate v4 diagnostic keeps the original model and code
path and reallocates three timing buckets, without expanding the 60-word
record, touching peer firmware, or using host inference.

* Matrix: the full prepare/dispatch/gather/finish sequence, 496 intervals
  per decode position across all 64 layers.
* Conv stage: actual worker admission, descriptor staging, dispatch, the
  controller's own convolution and all convolution completions, 48 intervals.
* GDN stage: actual descriptor staging, rendezvous/dispatch and all recurrent
  state completions, 48 intervals.
* Dense attention: the preparation, attention and KV append before the
  output projection (16 intervals). Dense and recurrent residual buckets
  still include all other layer work and their respective owner checks.

These are exclusive elapsed-controller-cycle buckets, not isolated engine
latencies, data-link bandwidth or proof of what the workers do during a
wait. Conv/GDN includes orchestration; early admission outside both remains
in the old recurrent bucket. Generation only, not prompt or weight load.
The v4 schema cannot be read as a v3 record.
