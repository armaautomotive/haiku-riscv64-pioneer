Qwen3.8-27B small recurrent projection layout proposal, 2026-11-12

Each of the 48 recurrent layers has alpha and beta Q8 matrices with 48
real rows. The simulated BFP8 matrix worker consumes whole 32-row tiles,
requiring 64 rows including 16 zero-padded rows per matrix. At 5,440 bytes
per BFP8 row, each needs 348,160 bytes; the original 48 Q8 rows occupy
276,480 bytes. Therefore the existing reservation cannot simply be reused.

PioneerQ38HybridSmallRecurrentBfp8Plan is an offline proposal which appends
the 96 padded tensors after their respective banks' existing high-water
marks, checks capacity, and preserves every other proposed allocation and
address. It adds 33,423,360 bytes (31.875 MiB) of address space; original
small-matrix reservations are left as holes. A synthetic canonical layout
test checks all 96 positions, unchanged non-target allocations, capacity,
malformed geometry refusals and isolation from native/Work/reference roles.

This is geometry only: the prepared cache, upload authorization, device
ledger, ROOT dispatch and Work path do not yet use it. No driver is changed,
and no card execution, model quality or inference-speed result is claimed.

Follow-up: a fixed-size, heap-only independent reconstruction now agrees
with every proposed part and all 96 relocated matrices. An isolated ledger
inspection sorts physical addresses before checking non-overlap, page
coverage, holes and digest, because the relocated tensors appear later in
bank memory than their original model order. Synthetic ASan/UBSan checks
cover 5,067,109 pages plus missing/extra/modified ledger refusals. This is
still not a native ledger, upload authorization, readback or hardware run;
the FNV digest is a consistency check, not cryptographic authentication.

Receipt follow-up: an isolated synthetic owner now walks the relocated
weight allocations in physical bank/address order, binds each span to its
owner/lease, records exactly 5,067,109 pages, and seals against the sorted
ledger. ASan/UBSan tests cover wrong owner/offset, unexpected ledger pages,
source revalidation and quarantine after an uncertain transfer. This is not
a live ioctl, actual upload, device readback or accelerator ownership grant.

Staging follow-up: the prepared-page chain now has a separate bounded
physical-order staging plan. It derives and checks every destination against
the canonical relocated layout, stages up to 256 pages in 16-page reads,
publishes data and metadata atomically, and stops permanently on an uncertain
acknowledgement. A full synthetic 21,475-span test matched each span against
the independently constructed receipt and exercised failed reads and
uncertain completion; a prepared-page-chain binding regression also passed.
This is host-side staging logic only, not an ioctl, physical transfer or
performance result.

Span-service follow-up: a new inspection-only receipt specialization passes
the staged first span through the existing checked span service using the
actual simulated transport image. Strict and Work-style transport modes pass;
a simulated packet failure quarantines the synthetic owner, and repeated
upload is refused. The pre-existing recurrent span-service regression also
passes. Only the first staged span was exercised through this service; the
full 21,475-span ordering was checked separately. This adds no live ioctl,
driver capability, actual device write or inference-speed result.

Workspace/receipt binding follow-up: metadata construction now requires
the synthetic receipt to be sealed and its full page ledger revalidated,
then compares the independently derived relocated proposal with the receipt's
own fixed reconstruction before and after constructing the 96 ROOT records.
Tests cover mismatched owners, changed proposals, overlapping destinations,
changed ledgers and atomic publication. This remains an inspection-only
metadata bridge: FNV consistency is not cryptographic authentication or
physical readback, and no native workspace write/driver authority is granted.
