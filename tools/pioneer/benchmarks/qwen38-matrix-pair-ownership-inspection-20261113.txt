Two-core learned-band ownership inspection, 2026-11-13

The single-core real-QKV band diagnostic cannot run concurrently: its lease
requires all cores held even during its cleanup. This separate initially offline
prototype snapshots two disjoint core images, stages both before releasing
either, rechecks the held fleet, starts both, and observes both before holding
either. It restores both L1 images and the original shared host TLBs only
after both terminal proofs and a fresh all-cores-held check. Once an I/O or
proof fails, it retains ownership and attempts no retry or cleanup.

The ASan/UBSan mock test requires both starts before publishing either fake
completion. It injects precomputed output words to check routing (not matrix
arithmetic), verifies both complete L1 snapshots and TLB restoration, and
checks ten timeout, status, reset, write, mapping and source-failure cases.
Explicit inspection-role tests reject kernel, driver, Work and validation builds.
The learned QKV export identity is checked without publishing its bytes.

Follow-up: the same two-core owner has also run the pinned real-QKV band
instruction image twice in the host RV32/matrix instruction simulator, with
two distinct learned-weight samples and separate L1 images. The simulated
device waits until both are released before serial host execution; all 128
returned words match the existing expected results, and both L1 images and
shared TLBs are restored. ASan/UBSan passed. This does not emulate hardware
timing, overlapping device execution, PCIe windows or reset races.

Cross-route alias hardening: per-core verification alone would not detect a
second staged image overwriting an aliased first core. The owner now rejects
identical sample selections and rereads both complete images after staging
both, before any reset/release. A fake-MMIO test forces the two routes to the
same L1 and confirms refusal, no processor release and retained quarantine for
all three distinct pairs of pinned QKV samples. It does not prove real
hardware routing or detect every conceivable partial alias of equal bytes.

Diagnostic bridge, build-only: a separate pair protocol and adapter with tag
2026111300010153 and fixed samples 0 and 1 now cross-compile for Haiku RISC-V.
The separate CPU-reference debug client authenticates the original model and
requires both 64-word outputs to match before it sends explicit END. Work and
validation role guards remain disjoint. The original single-core diagnostic
also cross-compiles. The committed source was exported with git archive and
independently built twice: both pair drivers have SHA-256
1ce9094e63f8b396bde385323e5e9b73da767aa496347375f620ae8e8825b3d1 and both
debug clients 81ffae39112c10e910be51aee6b63bdd139e143543e1da0fdb4d77b540845eaa.
This pins build inputs but does not authorize installation.

The actual pair debug client was compiled under ASan/UBSan against fake source
and ioctl endpoints. It refused invalid metadata, source readiness failures,
run and END failures, corrupted state and restoration flags for both peers,
and all 128 individually corrupted output positions without sending END after
a failed run. No real device was opened. The extracted actual kernel pair
Control/Reply/Fault/Dispose/Free code also passed 35 ASan/UBSan scenarios
with fake device and lease endpoints. These cover rejected requests, both
result buffers on quarantine, lost run reply, explicit END, failed END and
no cleanup after uncertain ownership. The original single-core extracted
controller passed 32 cases. This is not a physical MMIO fault test.

The one-shot parent now requires the pinned stable/diagnostic artifacts and
independent QKV source/reference, authenticates before swapping, and checks
all 128 returned words against that separate reference before restoring the
stable driver. Its actual flow passed 398 fake-endpoint cases, including
missing, duplicated and wrong individual words and failures before/after the
swap. The client prints returned words only after its explicit successful END.
This wrapper has NOT been run on hardware; build provenance for the updated
client, live check-only admission, and actual overlap proof remain required.

This is NOT a physical two-core test, 119-core cohort,
model inference, numerical qualification or speed measurement. In particular,
real overlap and completion behavior must be established on hardware after
an independently reviewed diagnostic adapter and containment tests. No
Assistant or installed driver changed. This prototype does not yet move any
Qwen layer to the P100A and does not establish improvement in tokens/second.
