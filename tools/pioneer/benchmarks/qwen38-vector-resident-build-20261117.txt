Qwen 27B: resident requests with unchanged vector92 compute (tag210)
==================================================================

Goal: avoid a second 19,399,024,640-byte raw weight upload when testing
another request. This is separate from output-head batching and does
not target steady decode rate. Nothing was staged on the Pioneer.

The distinct tag210 pairs vector92's four ROOT and ten peer arrays with
the existing resident request lifecycle. It does not change the legacy
tag91 resident or tag92 one-shot selections. Request close still restores
the L1, code, host, PCI and clock scopes. The same FD can then open a fresh
mutable request context while retaining the read-only weight reservation.
Explicit model END still owns final unreserve. CPU vocabulary/text work
is unchanged; there is no host inference, comparison, or fallback.

Assistant install. Its separately bound resident rate client sends two
matched public counting requests in one worker, checks the exact

requires explicit model END and actual worker exit0. It distinguishes
resident request closure from END and checks raw timing arithmetic. It
reports per-request host time separately; unavailable rates stay unavailable.
An unknown IPC/device outcome is close-only, not retry, END or reset.
